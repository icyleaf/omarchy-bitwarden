# ADR 0032: Cipher Custom Fields and Multiple Login URIs Mutation Lifecycle

## Status
Accepted

## Context
Following the implementation of end-to-end cipher mutation workflows for Login and Secure Note items (ADR-0027, PRs #326–#330), Omawarden provided terminal creation (`vault create`), direct editing (`vault edit`), optimistic concurrency verification, and safe deletion (`vault delete`). 

However, mutation support was restricted to primary scalar attributes (`name`, `username`, `password`, `notes`, `folder_id`, `favorite`, and a single primary `uri`). It omitted two critical Bitwarden data primitives:
1. **Custom Fields (`fields`)**: Arbitrary key-value metadata attached to any cipher, categorized into Text (Type 0), Hidden/Secret (Type 1), Boolean (Type 2), and Linked (Type 3).
2. **Multiple Login URIs (`login.uris`)**: A login item may associate multiple website endpoints, domains, or hostnames with individual match detection rules.

### Ecosystem Reference Analysis
- **Official Bitwarden CLI (`bw`)**: Provides complete data fidelity by exposing raw item JSON templates (`bw get template item`). However, mutating custom fields or URIs requires piping payloads through external tools (`jq`) and Base64 encoders (`bw encode`), which is cumbersome and error-prone for interactive terminal users.
- **Rust Client Precedent (`rbw`)**: Prioritized human-friendly workflows (`rbw add`, `rbw edit`) using `$EDITOR`, but historically restricted `$EDITOR` buffers to the password and notes alone (Issues #141, #365). Users could neither inspect nor edit custom fields and secondary URIs from the terminal, forcing reliance on the web vault.

Omawarden required a design that combines the structural fidelity of `bw` with the streamlined terminal ergonomics of `rbw`, without inheriting their respective limitations.

## Decision

We establish a comprehensive architecture for Custom Fields and Multiple Login URIs across the daemon IPC wire protocol, cryptographic engine, interactive editor, and CLI interfaces:

### 1. Data Schema & Cryptographic Invariants
- **Upstream Alignment**: Omawarden aligns its wire representation with the Bitwarden API specification:
  - `fields`: Top-level array of objects `[{"name": String, "value": String, "type": u32}]`.
  - `uris`: Array of objects under `login.uris`: `[{"uri": String, "match": Option<u32>}]`.
- **Zero-Knowledge Encryption Boundary**:
  - The daemon is solely responsible for encryption and decryption. Plaintext custom field names, values, and URI strings MUST NEVER cross the HTTP boundary unencrypted.
  - In `encrypt_cipher` (creation) and `encrypt_cipher_update` (modification), each field's `name` and `value`, and each URI's `uri` are encrypted with the cipher's symmetric key.
  - In `cipher_update`, omitted top-level fields preserve their existing values, preventing accidental erasure of unmentioned metadata.

### 2. Interactive Terminal Ergonomics (`$EDITOR`)
When invoking `omawarden vault edit <target>` without field flags in an interactive terminal:
- The editor template generated by `format_editor_template` surfaces all URIs and Custom Fields in structured, human-readable sections:
  ```text
  # Editing login cipher: GitHub (uuid-xxx)
  Name: GitHub
  Username: octocat
  Password: ••••••••
  URI: https://github.com
  URI: https://api.github.com
  Folder: 
  Favorite: false

  # Custom Fields:
  Field: PIN = 1234
  Hidden Field: Recovery Code = sec-98765
  Bool Field: Requires VPN = true

  # Notes (everything below this line is treated as notes):
  My notes here...
  ```
- **Parsing & Sync Invariant**:
  - Multiple `URI:` lines are parsed into `login.uris` in source order.
  - Lines prefixed with `Field:`, `Hidden Field:`, or `Bool Field:` are parsed into typed custom fields.
  - Exiting the editor replaces the cipher's `uris` and `fields` with the parsed collection.

### 3. Command-Line Mutation Syntax
For scripted automation and non-interactive execution:
- **Creation (`vault create login` / `vault create note`)**:
  - Repeatable `--uri <URL>` flags for login ciphers (e.g. `--uri https://github.com --uri https://api.github.com`).
  - Repeatable typed field flags for login and note ciphers:
    - `--field <NAME=VALUE>` (Text, Type 0)
    - `--hidden-field <NAME=VALUE>` (Hidden, Type 1)
    - `--bool-field <NAME=true|false>` (Boolean, Type 2)
  - Full JSON pipelines via `--stdin` and `--from-json` accept unencoded JSON payloads.
- **Editing (`vault edit <target>`)**:
  - **Custom Fields (Name-based Upsert)**: Specifying `--field`, `--hidden-field`, or `--bool-field` updates the existing field with that name or appends it if absent.
  - **Field Removal**: Repeatable `--remove-field <NAME>` removes matching custom fields by name.
  - **URI Modification**: Passing `--uri <URL>` replaces the URI list. Providing `--add-uri <URL>` appends to existing URIs without replacing. Providing `--clear-uris` removes all URIs.

### 4. Clipboard & Inspection Integration
- `omawarden copy <target> --field <NAME>`:
  - Resolves target custom fields by exact or case-insensitive name match.
  - Transmits sensitive values (Hidden fields) to the platform clipboard under active Clipboard Guard protection with automatic TTL zeroization.

## Consequences

### Positive
- **Parity with Web Vault**: Eliminates the need to switch to browser extensions or web interfaces for managing multi-domain services, API tokens, security questions, or custom PINs.
- **Superior Terminal Ergonomics**: Solves the historical pain point in `rbw` (where `$EDITOR` excluded fields) and avoids the tedious `jq` + `bw encode` dance required by `bw`.
- **Preserved Cryptographic Invariants**: All sensitive custom field values and names are encrypted with the cipher key before persisting to local cache or dispatching to upstream servers.

### Negative / Trade-offs
- CLI flag count increases slightly on `create` and `edit` commands to accommodate `--field`, `--hidden-field`, `--bool-field`, and `--remove-field`.
- The editor parser must handle malformed custom field declarations gracefully, reporting descriptive line numbers when format violations occur.
